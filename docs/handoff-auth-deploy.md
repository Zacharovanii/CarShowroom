## 4. Что менять в конфиге

*Сделано (D27).* Фактический конфиг шире наброска ниже: ещё `sendOnSignIn: true`,
`resetPasswordTokenExpiresIn: 3600`, `revokeSessionsOnPasswordReset: true`, `rateLimit`;
ссылки в письмах ведут на страницы фронта, а не на `url` от Better Auth.

Имена опций проверены по типам установленного пакета
(`node_modules/@better-auth/core/src/types/init-options.ts`), а не по памяти.

В `apps/api/src/auth/auth.ts`:

```ts
emailAndPassword: {
  enabled: true,
  requireEmailVerification: true,      // без подтверждения сессия не создаётся
  sendResetPassword: async ({ user, url, token }) => { /* письмо */ },
},

emailVerification: {
  sendOnSignUp: true,                  // письмо сразу при регистрации
  autoSignInAfterVerification: true,   // перешёл по ссылке — сразу вошёл
  expiresIn: 3600,                     // час жизни ссылки
  sendVerificationEmail: async ({ user, url, token }) => { /* письмо */ },
},
```

**Миграции не нужны.** Таблица `verifications` и колонка `users.email_verified`
уже заведены первой миграцией и отображены в конфиге (`fields: { emailVerified:
"email_verified" }`). Проверить: `apps/api/db/migrations/`.

## 5. Чем отправлять письма

| Вариант | За | Против |
| --- | --- | --- |
| **Resend** | ключ за минуту, есть бесплатный лимит | внешняя зависимость; тестовый домен шлёт только владельцу аккаунта — нужен свой (под)домен |
| SMTP + nodemailer | любой ящик, в том числе корпоративный | DKIM/SPF руками, иначе письма уходят в спам |
| Вывод ссылки в лог | ноль зависимостей | не боевое решение |

*Выбран Resend (D27), REST простым `fetch`, без SDK.* Рекомендация «Resend на тестовом
домене, DNS не нужен» была **неверной**: отправитель `onboarding@resend.dev` доставляет
только на адрес владельца аккаунта Resend, любой другой получатель — ошибка. Для
реальных адресов нужен свой подтверждённый (под)домен: добавить его в панели Resend
и прописать выданные DNS-записи (SPF, DKIM). Тестовый домен годится только для
проверки на собственном ящике.

Переменные — `RESEND_API_KEY` и `MAIL_FROM` (`CarShowroom <noreply@ваш-домен>`) в `envSchema`
и `.env.example`. В production обе обязательны, без них API не стартует. Без ключа (dev,
тесты) письма не уходят, ссылка пишется в лог API (`[Mail]`).

## 7. Чек-лист выкатки, помимо почты

- **Новый `BETTER_AUTH_SECRET`.** Сейчас в `.env` лежит `spike-s2-local-secret-change-me`,
  и он в истории гита. Сгенерировать: `npx @better-auth/cli secret`.
  *Закрыто (D28):* секрет генерируется на сервере в `docker/.env`
  (`openssl rand -base64 32`), dev-секрет на проде не используется.
- **`BETTER_AUTH_URL`** — боевой домен по HTTPS. Без HTTPS cookie с `secure` не поставится.
  *Закрыто (D28):* compose собирает его из `SITE_DOMAIN` как `https://${SITE_DOMAIN}`.
- **`trustedOrigins`.** Если фронт и API на одном origin (Nest раздаёт статику), хватит
  `BETTER_AUTH_URL`. Если домены разные — обязательно задать `WEB_ORIGIN`, иначе будет
  403 `INVALID_ORIGIN`. **Эту ловушку в проекте уже ловили** — см. коммит
  `fix(api): доверенный origin фронта в dev-режиме` и раздел 8 ниже.
  *Закрыто (D28):* один origin — фронт отдаёт Caddy, `/api` он проксирует в Nest на том же
  домене; `WEB_ORIGIN` на проде не задаётся. Ловушка §8 остаётся: проверять из браузера.
- **Ограничение частоты.** *Включено (D27):* вход и регистрация 5/60 с, письма 3/60 с,
  остальное 100/60 с, ответ 429. **IP клиента Better Auth берёт только из `X-Forwarded-For`**
  (с одним адресом: цепочку без `trustedProxies` отбрасывает). ~~nginx перед API:
  `proxy_set_header X-Forwarded-For $remote_addr;` — не `$proxy_add_x_forwarded_for`.~~
  Без этого, или если API открыт напрямую, все посетители делят один бакет: пять входов
  в минуту на весь сайт. Проверить после выкатки: шесть входов подряд с одного адреса →
  429, с другого — проходит.
  *Закрыто (D28):* перед API не nginx, а Caddy — он сам ставит `X-Forwarded-For` адресом
  клиента и отбрасывает входящий (`trusted_proxies` не задан), настройки не нужно; API
  наружу не опубликован. Проверка 429 — в чек-листе [deploy.md](deploy.md), шаг 11.
- **Почта.** В `.env` сервера: `RESEND_API_KEY`, `MAIL_FROM` с адресом на своём
  подтверждённом домене (§5). Без них API в production не стартует.
  *Закрыто (D28):* обе — обязательные поля `docker/.env` (compose без них не запустится).
  Подтвердить домен `tda-char.site` в Resend — руками, до выкатки.
- **Порт базы.** `docker/compose.yml` отдаёт 5434 наружу (стандартный 5432 часто занят).
  *Закрыто (D28):* на проде `docker/compose.prod.yml`, порты у базы и MinIO не
  публикуются; наружу только Caddy (80/443).
- **Пометка «учебный проект, не официальный сайт BMW»** в подвале уже стоит (D1) —
  на публичном домене она обязательна.
- **Статика.** Nest раздаёт `apps/api/public` (D15.1). При выкатке проверить, что
  `/assets/cars/*.webp` и `/assets/models/*.glb` отдаются.
  *Закрыто (D28):* проверено локально — `/assets/cars|models` отдаются, без
  licensed-assets — заглушки. Фронт собирается в `/static/`, `/assets/*` целиком у API.
  На сервере licensed-assets кладутся руками — [deploy.md](deploy.md), шаг 8.

Что остаётся сделать руками на сервере — всё по [deploy.md](deploy.md): подготовка VPS,
DNS, `docker/.env`, первый запуск, первый админ, проверка.

## 8. Ловушка, на которой тут уже обожглись

Better Auth сверяет заголовок `Origin` со списком доверенных. Проверка curl-ом это
**скрывает**, если подставить `Origin` самого API — то есть заголовок, который браузер
никогда не пришлёт. В этом проекте так и вышло: три агента отчитались, что
«авторизация проверена», а в браузере вход возвращал 403.

Правило: любую проверку авторизации гнать **через тот же origin, с которого пойдёт
браузер**, и хотя бы раз открыть страницу руками.

## 9. Когда считать готовым

1. `npm run typecheck`, `npm run lint`, `npm run build` из корня — зелёные.
2. `npm test -w @carshowroom/api` — все тесты проходят (число могло вырасти).
3. На чистом ящике: регистрация → письмо пришло → переход по ссылке → вошёл.
4. Вход неподтверждённым пользователем даёт понятное сообщение и кнопку выслать заново.
5. Восстановление пароля проходит целиком: запрос → письмо → новый пароль → вход.
6. Seed-учётки входят без писем.
7. D27 записан, `use-cases.md` поправлен, `.env.example` содержит все новые переменные.

Пункты 3 и 5 на реальном ящике проверяются только после выкатки с ключом Resend
и своим доменом; локально — по ссылке из лога API (`[Mail]`).

## 10. Правила работы в этом проекте

- Коммит **только** после явного «коммить» в текущем сообщении; прошлое разрешение
  не переносится. Сообщения по-русски, `type(scope): описание`, без строк атрибуции.
- Типы запросов и ответов — только из `packages/contracts`.
- SQL руками через postgres.js, ORM не добавлять. Better Auth — исключение, у него
  свой `pg` Pool (D7.1).
- Схема БД меняется только миграциями (dbmate, чистый SQL).
- Стили — CSS Modules и только семантические токены, хардкод цветов, отступов,
  радиусов и длительностей запрещён.
