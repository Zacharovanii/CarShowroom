# Журнал решений

Архитектурные решения проекта в формате MADR-lite: контекст → решение → последствия →
альтернативы. Номера стабильны — на них ссылаются комментарии в коде; заменённое решение
сохраняет номер и пометку «Заменено Dxx». Как система устроена целиком —
[architecture.md](architecture.md).

---

## D1. Тема — дилерский центр BMW с 3D-просмотром

**Решение.** Учебный сайт дилерского центра BMW (неофициальный).

- Одна марка; каталог фильтруется по сериям, а не по маркам.
- Главный сценарий — запись на тест-драйв ([use-cases.md](use-cases.md)).
- На странице автомобиля — 3D-модель с перекраской кузова (D11, D25).
- В подвале — пометка «учебный проект, не официальный сайт BMW».

## D2. Монорепо на npm workspaces

**Решение.** Три пакета — `apps/web`, `apps/api`, `packages/contracts` — связаны
workspaces стандартного npm. Монорепо из трёх пакетов не нужны кеш сборок и граф задач,
только связь пакетов; инструмент не усложняется сверх того, что требует задача.

**Альтернативы.** pnpm — ещё один инструмент без выигрыша на трёх пакетах;
Turborepo/Nx — оркестрация сборок, которой здесь нечего оркестрировать.

## D3. Без React Server Components, фронт — SPA

**Решение.** SPA. React Router в **декларативном режиме** (`BrowserRouter`, `Routes`,
`Route`), данные — через TanStack Query; loaders/actions data-режима не используются,
чтобы не было двух механизмов загрузки данных.

**Контекст.** RSC в React Router экспериментальные и не работают в декларативном режиме,
а сервер между браузером и Nest — лишнее звено. Самая тяжёлая страница (3D) целиком
клиентская.

## D4. Бэкенд — NestJS

**Решение.** NestJS. Слои: controller → service → repository; для чистого чтения без
правил сервис можно не заводить (controller → repository).

**Контекст.** Модули, DI и guards закрывают то, что иначе собиралось бы руками:
глобальную проверку сессии, роли, пайпы валидации. TypeScript на обеих сторонах позволяет
делить один контракт (D8) между фронтом и бэком.

## D5. SQL руками через postgres.js

**Решение.** Прикладной SQL пишется руками через postgres.js. Репозиторий получает `sql`
(корневой или транзакционный из `sql.begin`) и возвращает строки; типы строк пишутся руками.

**Последствия.** Запрос в коде совпадает с тем, что выполняет база, — нет слоя ORM,
который генерирует SQL. Схема меняется только миграциями чистым SQL (D6).

**Альтернативы.** Prisma, TypeORM — лишний слой абстракции над схемой и запросами;
Kysely — типобезопасный, но это query builder, а не SQL.

## D6. Миграции — dbmate, чистый SQL

**Решение.** Файлы `apps/api/db/migrations/*.sql` с секциями `-- migrate:up` /
`-- migrate:down`. dbmate ставится npm-пакетом и пишет `apps/api/db/schema.sql` — дамп
схемы для ревью. Миграции применяются отдельной командой, не при старте приложения.

**Альтернативы.** node-pg-migrate (миграции в JS), самописный раннер.

## D7. Пользователи — Better Auth

**Решение.** Регистрация, вход, сессии и роли — Better Auth; остальное — свой код.

- Интеграция `@thallesp/nestjs-better-auth`: глобальный guard закрывает всё, публичное
  помечается `@AllowAnonymous()`; `bodyParser: false` — модуль сам подключает парсеры.
- Свой `pg` Pool внутри модуля `auth` (D7.1).
- **Схема под нашим контролем:** SQL из `npx auth generate` перенесён в первую миграцию,
  дальше — только миграции. Таблицы переименованы (`users`, `sessions`, `accounts`,
  `verifications`), колонки — snake_case, UUID генерирует Postgres.
- Сессия — httpOnly cookie; на фронте `createAuthClient` и поверх него свой `AuthContext`.
- Подтверждение email и сброс пароля — D27, роли — D16; OAuth выключен.
- **Схемы форм входа, регистрации и профиля — в `packages/contracts`** (UC-G5). Маршруты
  Better Auth — raw middleware в обход роутера Nest, поэтому на сервере схемы применяются
  его before-хуком: он проверяет поля с CHECK в БД и нормализует email.

**Контекст.** Требования: готовые регистрация, вход и роли; без ORM в коде проекта;
**пользователи лежат в нашей БД**, иначе `test_drives.user_id` перестаёт быть внешним
ключом на `users` (без FK, `on delete` и join в списке менеджера). Все три требования
закрывает только Better Auth.

**Альтернативы.** Своя реализация на argon2 + сессиях (много кода в чувствительной области);
Auth.js (построен вокруг OAuth, Credentials не регистрирует пользователей, ролей нет);
Lucia (депрекейтнута в 2025 году); Passport (только стратегии входа, остальное своё);
SuperTokens self-hosted (отдельный контейнер со своей БД); Keycloak, Zitadel, Ory Kratos
(полноценный IdP — несоразмерно задаче); Clerk, Auth0, Supabase Auth (пользователи
во внешнем сервисе).

## D7.1. Два драйвера Postgres

**Контекст.** Better Auth принимает инстанс драйвера (`pg`, `mysql2`, `better-sqlite3`),
диалект Kysely или адаптер ORM. postgres.js (D5) не подходит: другой API (tagged templates
вместо `query(text, values)`) и свой пул. Инвариант «SQL руками» относится к коду проекта,
а не к внутренностям зависимости: Kysely внутри Better Auth наш SQL не пишет.

**Решение.** Два пула: маленький `pg` Pool внутри модуля `auth` и postgres.js для всего
остального. `pg` наружу из модуля `auth` не выходит.

**Последствия.** `max` задан явно обоим пулам (`pg` — 5, postgres.js — 10);
`DATABASE_URL` читается дважды, при shutdown закрываются оба пула (`DatabaseModule`,
`AuthModule`). Общей транзакции между auth и прикладным кодом нет — пока не мешает:
`phone` лежит в `users` (`additionalFields`), отдельной таблицы профиля нет.

**Альтернативы.** Всё на `pg` (прикладной SQL через `$1, $2` и массив значений, без
`sql.begin`); всё на postgres.js через community-диалект `kysely-postgres-js` (лишняя
непротестированная зависимость в самом чувствительном месте); свой адаптер через
`createAdapter` (200+ строк в области, ради которой берётся библиотека).

## D8. Общие типы — `packages/contracts` на zod

**Решение.** Контракт описывает **JSON на проводе**: даты и деньги — строки. В пакете —
zod-схемы запросов и ответов, выведенные типы, формат ошибки, enum-ы и общие правила
(например, лимит TD-6). Бэкенд валидирует body/query/params этими схемами через свой
`ZodValidationPipe`; фронт берёт из пакета типы API-клиента и схемы форм. Ответы на фронте
в рантайме не парсятся. Пакет собирается `tsc` (D20).

**Альтернативы.** Общие DTO-классы Nest (декораторы и `reflect-metadata` в бандле фронта,
типы не совпадают с JSON для дат и `numeric`); openapi-typescript (нужен, когда бэкенд
не на TS); ts-rest/oRPC (ещё один слой; при необходимости добавляется поверх тех же схем).

## D9. Swagger не добавляем

**Решение.** Без Swagger: схемы описаны в zod, а `@nestjs/swagger` работает
на декораторах классов — каждый эндпоинт описывался бы дважды. Ручная проверка API —
`.http`-файлы в `apps/api/http/` (REST Client, JetBrains), автоматическая — тесты (D14).
Если понадобится документация API, OpenAPI генерируется из zod-схем (zod 4 умеет
JSON Schema).

## D10. Стили — CSS Modules + собственная дизайн-система на токенах

**Решение.**

- `apps/web/src/styles/tokens.css` — два уровня переменных: примитивы (шкалы цветов,
  отступы, радиусы, шрифты, тени, длительности) и семантика (`--color-bg`, `--color-fg`,
  `--color-primary`, `--focus-ring` и т.д.). Компоненты используют семантические токены.
- `components/ui/*` — свои примитивы; варианты — через `data-variant` / `data-size`.
- Поведение сложных компонентов (Dialog, Select, Tabs, Toast, Checkbox) — **Radix
  Primitives** без стилей.
- Брейкпоинты — фиксированные значения, записанные в `tokens.css` комментарием.

**Контекст.** Своя дизайн-система на токенах: стили изолированы в модулях, в разметке
нет утилитарных классов, хардкод цветов и отступов запрещён (инвариант). Справочник по
токенам и компонентам — [design-system.md](design-system.md).

**Альтернативы.** Tailwind + shadcn — готовые утилитарные классы в разметке вместо своей
системы токенов; CSS-in-JS — рантайм-стоимость без выигрыша для SPA.

## D11. 3D — React Three Fiber + drei

**Решение.**

- `@react-three/fiber` + из `@react-three/drei` — `useGLTF`, `CameraControls`,
  `ContactShadows`; окружение сцены (студия, HDRI-панорамы) — свои компоненты.
- Модели — GLB, 3D есть у каждого автомобиля (D25). Цвет кузова меняется через `color`
  материала краски, имя материала хранится в БД (`paint_material`).
- Сцена и three.js грузятся лениво (`React.lazy`, отдельный чанк) при открытии вкладки «3D».
  Без WebGL или при ошибке — галерея фото.
- Декодер Draco не подключается: модели не сжаты, а `useGLTF` тянул бы его с внешнего CDN.

**Альтернативы.** `<model-viewer>` от Google — вращение и смена материала из коробки, но
почти без контроля над сценой (свет, камера, тени).

## D12. Деньги считает бэкенд

**Решение.** Цены хранятся в `numeric` и отдаются строками; фронт только форматирует строку.
У автомобиля одна цена, конфигуратора нет (D18) — считать на фронте нечего.

**Альтернативы.** Расчёт на фронте — `Number` на деньгах и два источника истины.

## D13. Упрощения (сознательно не делаем)

- Нет записи по звонку — клиент записывается сам через сайт.
- Нет покупки и оплаты, OAuth, i18n, уведомлений о записях; письма только служебные (D27).
- Нет избранного и сохранённых конфигураций (D18).
- Нет удаления пользователей — только блокировка; нет аудит-лога — только поля «кто/когда».
- Одна тема оформления (D21).
- Нет Storybook — витрина компонентов на dev-странице `/__ui`.

## D14. Dev-окружение

**Решение.**

- Vite dev-сервер проксирует `/api`, `/assets`, `/media` на Nest — фронт и API на одном
  origin: нет CORS, cookie Better Auth работают без настройки SameSite.
- Node 24, TypeScript strict везде, ESLint (flat config) + Prettier.
- Тесты — Vitest в `apps/api`: юнит (`src/**/*.spec.ts`) и e2e через supertest
  (`test/*.e2e.spec.ts`); `unplugin-swc` не нужен. Автотестов фронта нет.
- Отдельной тестовой БД нет: e2e работают с dev-базой (`DATABASE_URL` из `apps/api/.env`)
  и убирают свои данные по префиксу `e2e-`. Перед тестами нужны поднятая БД и миграции.

## D15. Хранение 3D-моделей и фото

**Статус:** заменено D15.1 и D26.

Хранилище выбирается по тому, кто пишет файлы: файлы проекта (seed и заглушки) — статика
из `/assets` (D15.1, D25); файлы, загруженные админом, — S3-совместимое хранилище,
раздача из `/media` (D26). Модель скачивается клиентом только при открытии вкладки 3D,
где бы файл ни лежал.

## D15.1. Статику раздаёт Nest из `apps/api`

**Решение.** `/assets/*` отдаёт процесс Nest (`app.useStaticAssets` в `main.ts`, без новых
зависимостей). Порядок поиска: `apps/api/licensed-assets/` (вне гита, D25) →
`apps/api/public/` (заглушки и HDRI из репозитория) → заглушка по типу:
`placeholder-car.webp` для `/assets/cars/*`, `placeholder-car.glb` для `/assets/models/*`.

**Последствия.** Одинаково в dev и проде, без шага копирования: путь считается
от `dist/main.js`. Фронт ходит на `/assets` через прокси Vite (D14) или Caddy (D28).
В БД — относительный путь, раздачу можно перенести в прокси без правки кода и данных.
Долгого кеша у `/assets` нет: файлы не версионируются.

**Альтернативы.** Отдельный веб-сервер для десятка файлов — лишний конфиг в dev и проде.

## D16. Роли: user, manager, admin

**Решение.**

- Admin-плагин Better Auth (`role`, `banned`/`ban*`, `createUser`, `listUsers`, `setRole`…);
  роль `manager` — через `createAccessControl`, `admin` включает права менеджера.
- На бэкенде — `@Roles([...])` из `nestjs-better-auth` поверх глобального guard.
- Менеджера создаёт админ, сразу с подтверждённым email (D27).
- Роль `admin` через интерфейс не назначается. В dev админ создаётся seed-скриптом;
  на проде первый админ регистрируется на сайте и повышается скриптом `promote-admin.mjs`
  в контейнере API (D28; локально — `npm run db:promote-admin`).
- Удаление пользователей (`removeUser`) не используется — только блокировка.

## D17. Деплой

**Статус:** заменено D28.

Один сервер, всё в docker compose, обязательный HTTPS (secure-cookie сессии). Конкретная
схема — прокси, сборка, миграции — в D28.

## D18. Объём: одна цена у автомобиля, минимум сущностей

**Контекст.** Комплектации, палитра с доплатами, избранное, сохранённые конфигурации,
настройки салона и правила тест-драйва в триггерах не нужны ни одному сценарию
из [use-cases.md](use-cases.md), а правила в plpgsql дублировали бы правила в API.

**Решение.**

- **Один автомобиль — одна цена** в `cars`; комплектаций и конфигуратора нет.
- **Избранного и сохранённых конфигураций нет.**
- **Цвет — только внешний вид 3D-модели**: `car_colors` — многие-ко-многим без доплаты.
- **Правила тест-драйва — в коде** (константы в `packages/contracts` и сервис API). В БД —
  CHECK-и и частичный уникальный индекс занятости слота: он решает гонку.
- **Настроек салона нет** — часы работы, горизонт, лимит и часовой пояс `Europe/Moscow`
  заданы константами.
- **У менеджера список записей на день**, а не недельный календарь.
- **Админ** заводит менеджеров, смотрит пользователей и управляет каталогом (D26);
  блокировки и смены ролей в интерфейсе нет.

**Последствия.** 12 таблиц — [db/README.md](db/README.md).

## D19. Ключи — суррогатные, значение фильтра в URL — id

**Решение.** Везде суррогатный `id` (`bigint generated by default as identity`; у таблиц
Better Auth — `uuid`, его диктует библиотека). Ключ — всегда `id`, внешний ключ —
`<таблица>_id`. Исключение — `car_colors`: составной PK `(car_id, color_id)`, суррогатный
ключ у таблицы-связи без атрибутов ничего не даёт.

**Контекст.** Натуральный ключ (`body_types.code = 'suv'`) экономит join и делает URL
читаемым, но требует гарантии, что значение уникально и не изменится. Суррогатный ключ
такой гарантии не требует; цена — один join по справочнику из нескольких строк.

**Последствия.** Значение фильтра в URL — `id` (`/catalog?body=6`), справочники приходят
из `/api/catalog/filters`. **Порядок строк в справочных данных менять нельзя**, только
дописывать в конец: неверный id покажет не пустой результат, а другой кузов. `slug` есть
только у `cars` — это адрес страницы. Подробнее — [db/README.md](db/README.md).

## D20. ESM везде, `contracts` собирается обычным `tsc`

**Решение.** Все три пакета — ESM. `packages/contracts` собирается `tsc` (один формат
и декларации), без бандлера.

- В `apps/api` и `packages/contracts` свои файлы импортируются с расширением `.js`
  (`./app.module.js`), хотя на диске `.ts`, — этого требует `moduleResolution: "nodenext"`.
  На импорт пакетов правило не распространяется.
- Один линтер — ESLint; `oxlint` из шаблона Nest удалён.

**Контекст.** Nest 12 по умолчанию генерирует проект на ESM + Vitest, Vite — тоже ESM.
С общим форматом контракты не нужно собирать дважды с ветвлением в `exports`.

**Альтернативы.** Nest на CommonJS (двойная сборка контрактов без причины); tsup для
контрактов (лишний инструмент: `tsc` справляется сам); два линтера.

## D21. Тема тёмная; светлая — переопределением шкал

**Решение.**

- Основная тема — тёмная: на тёмном фоне фото и 3D-модель читаются как объект витрины.
- Светлая тема заготовлена блоком `[data-theme="light"]` в `tokens.css` (переключателя
  в интерфейсе нет): переопределяются **примитивные шкалы**, семантика наследуется; вручную —
  только роли, меняющие смысл при инверсии (подложка диалога, тени, первичная кнопка).
- Первичное действие — **светлая заливка с тёмным текстом**: белый на синем в тёмной теме
  не дотягивает до 4.5:1. Синий — цвет выбора и навигации.
- Кольцо фокуса — **всегда снаружи** контрола (`outline-offset`): поверх светлой кнопки
  синее кольцо даёт 2.3:1, со смещением — 7.4:1 по фону страницы.

**Последствия.** Пары цветов проверены по WCAG 2.1 AA, значения —
[design-system.md](design-system.md).

**Альтернативы.** Две независимые палитры (расходятся при первой правке); переопределение
только семантики (по два десятка строк на тему вместо нескольких на роль).

## D22. Условия тест-драйва (TD-8) проверяются только на клиенте

**Решение.** В диалоге записи два обязательных чекбокса — права категории B со стажем
от 2 лет и согласие на обработку персональных данных; без них «Подтвердить» выключена.
На бэкенд они не уходят: в `createTestDriveSchema` таких полей нет, документы проверяются
в салоне (TD-8).

**Последствия.** Отметка только на клиенте не является юридически значимым согласием;
для учебного проекта это допустимо.

**Альтернативы.** Колонки в `test_drives` (миграция и правка контракта ради поля, которое
никто не читает); отправка полей сверх контракта (расхождение фронта и схемы).

## D23. Упрощения в дизайне

- **Фильтр цены — два числовых поля** (`PriceRange`) вместо слайдера с двумя рукоятками
  (отдельная задача по клавиатуре и ARIA). Поля отдают `priceMin` / `priceMax` строками (D12).
- **Карточка каталога показывает только поля `carCardSchema`** (мощность, привод, тип
  двигателя); разгон и скорость — на странице автомобиля. Контракт каталога ради карточки
  не расширяется.
- **Атрибуции фото и моделей в интерфейсе нет**: автора и лицензии в БД нет,
  лицензированные файлы вне репозитория (D25).
- **Единая обработка фото** — токен `--photo-filter` выравнивает разнородные снимки,
  снимается одной строкой.

## D24. Иконки — Lucide, пакетом

**Решение.** Набор [Lucide](https://lucide.dev) (MIT), пакет `lucide-react` — в бандл
попадают только использованные иконки. Один набор, без смешения с другими; размеры
и толщина — токенами (`--icon-size`, `--icon-stroke`), цвет — `currentColor`. Текстовые
символы (`→`, `✓`, `✕`) вместо иконок не используются. Правила применения —
[design-system.md](design-system.md).

**Контекст.** Линия 2px постоянной толщины, прямые формы, сетка 24 — набор ложится
на систему без радиусов.

**Альтернативы.** Heroicons (скруглённее, хуже ложится на систему без радиусов); Material
Symbols (шрифт-иконки: лишний запрос и своя система размеров); собственный набор.

## D25. Лицензированные модели и фото — вне гита, в гите только заглушки

**Контекст.** Каталог — 18 автомобилей BMW, у каждого 3D-модель и несколько фото. Модели
(Ddiaz Design, Sketchfab) лицензированы только для некоммерческого использования, лицензия
фото не установлена. Публичный репозиторий — это распространение, поэтому ни то ни другое
в гит не попадает.

**Решение.**

- Лицензированные файлы — в `apps/api/licensed-assets/{models,cars}/` (в `.gitignore`),
  Nest отдаёт их под `/assets/` раньше `public/` (D15.1). Пути в seed:
  `/assets/models/{slug}.glb`, `/assets/cars/{slug}-{n}.jpg`. На сервере каталог
  монтируется в контейнер API только на чтение (D28).
- В репозитории — CC0-заглушки `public/assets/placeholder-car.{webp,glb}` (седан
  Quaternius) и HDRI Poly Haven. Чистый клон работает: каталог полон, вкладка 3D
  показывает заглушку и перекрашивает её.
- Материал краски во всех моделях назван `CarPaint` (`paint_material` в БД).
- Модели не сжимаются (3–22 МБ): грузятся только при открытии вкладки 3D (D11).

**Альтернативы.** `git update-index --skip-worktree` поверх заглушек с теми же именами
(флаг живёт в одном клоне и ломается на pull/checkout); Git LFS (всё равно публикация);
seed без `model_3d_path` по умолчанию (на чистом клоне пропала бы вкладка 3D).

## D26. Каталог управляется админом, файлы в MinIO

**Решение.** Админ заводит автомобили, правит поля и палитру, загружает фото и 3D-модель,
публикует и снимает с публикации. Seed — стартовое наполнение; seed-автомобили
редактируются как любые другие.

- **Хранилище — MinIO** (S3-совместимое, приватный бакет), клиент `@aws-sdk/client-s3`.
- **Загрузка и отдача — через Nest.** Загрузка — `multipart/form-data` в память,
  проверка, затем `PutObject`. Отдача — `GET /media/*` (вне `/api`, без авторизации)
  с `Cache-Control: immutable`: ключ с uuid уникален и не перезаписывается; 404 не кешируется.
- **Пути.** В БД — готовый путь `/media/<key>`, как и `/assets/...`; CHECK-и путей
  допускают оба префикса.
- **Порядок операций:** объект в MinIO → транзакция в БД → удаление старого объекта.
  Упала транзакция — удаляется новый объект; упало удаление старого — только предупреждение
  в лог. Файлы `/assets/...` не удаляются никогда.
- **Черновики.** Новая карточка не опубликована и публично не существует (404); публикация
  требует хотя бы одно фото (`409 CAR_NOT_READY`). Файлы черновика по прямой ссылке
  доступны — ключ с uuid нигде не публикуется.
- **Удаление** возможно только без записей на тест-драйв; иначе `409 CAR_HAS_TEST_DRIVES`
  (FK `restrict`) и предложение снять с публикации.
- **Проверка файлов — по сигнатуре**, а не по `mimetype`: фото JPEG/PNG/WebP/AVIF
  до 10 МБ, модель GLB v2 до 60 МБ с обязательным материалом краски
  (`400 PAINT_MATERIAL_NOT_FOUND`, D25).
- **Справочники не редактируются**: их id в URL фильтров (D19), палитра автомобиля —
  выбор из существующих `colors`.

**Последствия.** Трафик `/media` идёт через Node — при одном админе приемлемо. MinIO
наружу не публикуется, CORS не нужен. Чистый клон с пустым бакетом работает на
`/assets/...` (D25).

**Альтернативы.** Presigned URL (непроверенный файл в хранилище, второй шаг и чистка
брошенных загрузок, CORS); публичный бакет (второй origin, путь в БД привязан к адресу
MinIO); файлы на диске в `public/` (смешиваются с заглушками, теряются при пересоздании
контейнера); `bytea` в БД (раздувает базу и бэкапы); мягкое удаление вместо 409 (третье
состояние рядом с черновиком).

## D27. Подтверждение email и восстановление пароля, письма через Resend

**Контекст.** На публичном сервере регистрация на чужой адрес и отсутствие сброса
пароля недопустимы.

**Решение.**

- **Средствами Better Auth.** `requireEmailVerification: true`: регистрация только
  отправляет письмо; вход неподтверждённым → 403 `EMAIL_NOT_VERIFIED` и новое письмо
  (`sendOnSignIn`); переход по ссылке подтверждает адрес и входит
  (`autoSignInAfterVerification`). Сброс пароля отзывает все сессии. Ссылки живут час.
- **Без утечки адресов.** Запрос сброса, повторная отправка подтверждения и регистрация
  на занятый email отвечают так же, как для нового адреса.
- **Ссылки ведут на фронт** (`/verify-email?token=…`, `/reset-password?token=…`), страница
  сама вызывает API Better Auth. Ссылка прямо на API в dev поставила бы cookie на хост
  API (:3000), а не фронта (:5173). `origin` — заголовок `Origin` вызвавшего запроса, если
  он в `trustedOrigins`, иначе `BETTER_AUTH_URL`.
- **Письма — модуль `apps/api/src/mail/`** (обычные функции: `auth.ts` собирается
  до появления DI), отправка — REST Resend через `fetch`. `RESEND_API_KEY` и `MAIL_FROM`
  в production обязательны; без ключа и в тестах письмо пишется в лог и in-memory outbox,
  который читают e2e-тесты. Отправителю нужен свой домен с SPF/DKIM.
- **Ограничение частоты** — встроенный `rateLimit` Better Auth в памяти: общий лимит
  100 / 60 с, вход и регистрация — 5 / 60 с, отправка писем — 3 / 60 с, превышение — 429.
  Выключен при `NODE_ENV=test`. IP клиента берётся из `X-Forwarded-For`, поэтому прокси
  перед API должен ставить ровно один адрес клиента (Caddy делает это сам, D28) — иначе
  все посетители попадают в один бакет.
- **Менеджеры (`createManager`, UC-A2) и seed-пользователи** создаются сразу
  подтверждёнными.

**Последствия.** Регистрация заканчивается экраном «Проверьте почту»; страницы
`/verify-email`, `/forgot-password`, `/reset-password` (UC-G7, UC-G8); кнопки повторной
отправки ждут 60 с. Лимиты сбрасываются при перезапуске и не делятся между экземплярами
(экземпляр один).

**Альтернативы.** SMTP + nodemailer (DKIM/SPF и репутация отправителя вручную); только
ссылка в логе (на публичном сервере адрес никто не подтвердит); SDK `resend` (зависимость
ради одного `fetch`); `requireEmailVerification: false` (подтверждение ничего не решает).

## D28. Выкатка: Caddy, сборка на сервере, seed без тестовых пользователей

**Решение.** Один сервер, всё в docker compose (`docker/compose.prod.yml`), обязательный
HTTPS. Пошаговая инструкция — [deploy.md](deploy.md).

- **Caddy — reverse proxy с автоматическим HTTPS:** сертификат Let's Encrypt получает
  и продлевает сам, конфиг `docker/Caddyfile` — несколько строк. `X-Forwarded-For` ставит
  корректно (адрес клиента; входящий заголовок от недоверенного источника отбрасывает),
  поэтому ограничение частоты D27 работает по клиенту.
- **Один origin.** `/api`, `/api/*`, `/media/*`, `/assets/*` проксируются в Nest,
  остальное — статика SPA. `BETTER_AUTH_URL` собирается из `SITE_DOMAIN`.
- **Фронт собирается в `/static/`** (`build.assetsDir: "static"`), потому что `/assets/*`
  занят API (D15.1). `/static/*` — файлы с хешем, `immutable`; остальные пути —
  `index.html` с `no-cache`.
- **Сборка на сервере из git-клона**, один multi-stage `Dockerfile` с целями `api`
  (prod-зависимости, `dist`, миграции и seed) и `web` (образ `caddy` со статикой).
- **Наружу — только порты Caddy**; db, minio и api во внутренней сети (Docker публикует
  порты в обход ufw). Секреты — `docker/.env`, licensed-assets — bind-mount на чтение (D25).
- **Миграции — одноразовый сервис `migrate`** (профиль `tools`), запускается явно.
- **Seed на проде — `--catalog-only`**, без тестовых учёток с публичным паролем. Первый
  админ регистрируется на сайте и повышается скриптом `promote-admin.mjs` (только
  с подтверждённым email); роль читается из БД на каждом запросе.

**Последствия.** Миграции применяются строго до `up`: без таблиц Better Auth отвечает 500,
healthcheck `api` не проходит и Caddy не стартует. Если перед Caddy появится ещё один
прокси (например, Cloudflare), понадобится `trusted_proxies`. Эксплуатационные детали
(пароль БД, права на файлы, очистка образов, DNS) — в [deploy.md](deploy.md).

**Альтернативы.** nginx + certbot (два конфига, cron продления, `X-Forwarded-For`
перезаписывается вручную); сборка в CI и реестр образов (лишняя инфраструктура для одного
сервера); раздача фронта Nest-ом (прокси всё равно нужен ради HTTPS); общий `/assets/*`
для фронта и API (конфликт имён молча отдаёт не тот файл); seed-админ с публичным паролем.

## D29. Django-раздел «Авто с пробегом» — отдельный сервис со своей SQLite

**Контекст.** Практическая работа по Django (МДК 01.06) требует: виртуальное окружение,
своих моделей с миграциями `makemigrations` / `migrate` (включая вторую миграцию
и `sqlmigrate`), админку Django, шаблоны с Bootstrap и SQLite. Тему разрешили оставить
прежней, поэтому Django встраивается в CarShowroom, а не становится отдельным проектом.

**Решение.** `apps/used-cars` — отдельное Django-приложение с разделом объявлений
о продаже автомобилей с пробегом.

- **Своя база и свои миграции.** SQLite и миграции Django относятся только к этому
  разделу. В Postgres основного сайта Django не ходит: там схему по-прежнему меняет
  только dbmate (D6), а Django-модели с `managed=False` лишили бы работу главного,
  что в ней проверяют, — миграций.
- **ORM Django, шаблоны Django и Bootstrap** — только в этом разделе. Правила «SQL
  руками» (D5) и «CSS Modules + токены» (D10) относятся к `apps/api` и `apps/web`.
  Bootstrap перекрашен переменными `--bs-*` в цвета токенов сайта, чтобы раздел
  выглядел частью CarShowroom.
- **Общий адрес.** Все маршруты раздела начинаются с `/used/`, статика — с
  `/used/static/` (`/static/` занят сборкой фронта, D28). В dev Vite проксирует `/used`
  в Django **без** `changeOrigin`: Django сверяет `Origin` формы с `Host`, и `Host`
  должен остаться адресом фронта, иначе POST получит 403 CSRF.
- **Окружение — uv** (`pyproject.toml` + `uv.lock`) вместо `venv` + `requirements.txt`
  из ТЗ: то же виртуальное окружение, но версии зафиксированы с хешами, а прямые
  зависимости отделены от транзитивных. `requirements.txt` при необходимости даёт
  `uv export`.
- **Чистый клон работает** (D25): тестовые данные — фикстура `used_cars.json`, заглушка
  фото — своя SVG (иконка Lucide, ISC), а не картинка основного сайта.
- **Только dev.** На сервер раздел не выкатывается; ссылка «С пробегом» в подвале SPA
  показывается только в dev-сборке (`import.meta.env.DEV`).

**Последствия.** У сайта два бэкенда и две базы, но они не связаны ни данными, ни
пользователями: вход в админку Django — свои суперпользователи. Объявления не знают
о каталоге новых автомобилей. Выкатка раздела потребует сервиса в compose (gunicorn),
маршрута `/used/*` в Caddy и тома для SQLite.

**Альтернативы.** Django поверх Postgres сайта с `managed=False` (нет своих миграций,
нарушается D6); переписать часть API на Django (дублирование, два источника правды
для одних данных); отдельный проект с другой темой (теряется связь с основным сайтом).
