# Решения

Формат: что решили → почему → что отвергли. Статус `принято` — действует; `проверить` —
принято, но подтверждается пробой (spike) на старте, до основной реализации.

---

## D1. Тема — дилерский центр BMW с 3D-просмотром

**Принято.** Одна марка — BMW; фильтрация по сериям вместо марок. Главный сценарий —
запись на тест-драйв (см. [use-cases.md](use-cases.md)). 3D только на странице автомобиля,
для 2–3 моделей; у остальных — галерея фото. В подвале пометка «учебный проект,
не официальный сайт BMW».

Отвергнуто: салон красоты — надёжнее, но визуально слабее; мультибрендовый салон —
размывает стиль.

## D2. Монорепо на npm workspaces

**Принято.** `apps/web`, `apps/api`, `packages/contracts`. npm уже стоит, workspaces
хватает для трёх пакетов.

Отвергнуто: pnpm (ещё один инструмент), Turborepo/Nx (избыточно для трёх пакетов).

## D3. Без React Server Components, фронт — SPA

**Принято.** RSC в React Router до сих пор помечены как unstable, декларативный режим
их не поддерживает, а для нашего приложения это лишний сервер между браузером и Nest.
Самая тяжёлая страница (3D) — полностью клиентская, выигрыша почти нет.

React Router — **декларативный режим** (`BrowserRouter`, `Routes`, `Route`), данные —
через TanStack Query. Loaders/actions data-режима не используем, чтобы не было двух
механизмов загрузки данных.

## D4. Бэкенд — NestJS

**Принято.** Личная цель — попробовать Nest. Слои: controller → service → repository.
Для чистого чтения без правил сервис можно не заводить (controller → repository).

## D5. SQL руками через postgres.js

**Принято.** Полный контроль над запросами и схемой. Репозиторий получает `sql`
(корневой или транзакционный из `sql.begin`) и возвращает строки. Типы строк пишутся руками.

Отвергнуто: Prisma, TypeORM (лишняя абстракция), Kysely (хорошо, но это уже builder,
а цель — писать SQL).

## D6. Миграции — dbmate, чистый SQL

**Принято.** Файлы `apps/api/db/migrations/*.sql` с секциями `-- migrate:up` / `-- migrate:down`.
dbmate ставится npm-пакетом и пишет `db/schema.sql` — дамп схемы, удобно смотреть в ревью.
Миграции применяются отдельной командой, не при старте приложения.

Отвергнуто: node-pg-migrate (миграции в JS), самописный раннер.

## D7. Пользователи — Better Auth

**Проверить** (spike S2). Готовая регистрация/вход/сессии, остальное — своё.

- Интеграция `@thallesp/nestjs-better-auth` (community). Глобальный guard: всё закрыто,
  публичное помечается `@AllowAnonymous()`, пользователь — `@Session()`.
- Требуется `bodyParser: false` в `NestFactory.create` — модуль сам подключает парсеры.
- **Better Auth подключается через `pg` Pool, не через postgres.js.** Значит в проекте два
  драйвера: маленький `pg` Pool внутри модуля `auth` и postgres.js для всего остального.
  Это осознанная цена; наружу из модуля `auth` `pg` не выходит. Подробно — в D7.1.
- **Схема под нашим контролем:** `npx auth generate` выдаёт SQL — переносим его в нашу
  первую миграцию и дальше меняем только миграциями (`auth migrate` не используем).
- Таблицы переименовываем через `modelName` (`users`, `sessions`, `accounts`,
  `verifications` — `user` в Postgres зарезервированное слово), колонки — в snake_case
  через `fields`. `generateId: "uuid"`, UUID генерирует Postgres.
- Сессия — httpOnly cookie. Фронт использует `createAuthClient` из `better-auth/react`,
  поверх — свой `AuthContext` (требование ТЗ и единая точка для UI).
- Email-подтверждение и OAuth выключены.
- **Роли — admin-плагин Better Auth** (D16).
- **Формы входа, регистрации и профиля описаны в `packages/contracts`** (`auth.ts`) —
  UC-G5 требует одних правил на клиенте и на сервере. На бэкенде они применяются
  before-хуком самого Better Auth: его маршруты поднимаются как raw middleware в обход
  роутера Nest, `ZodValidationPipe` на них не навесить. Хук закрывает поля с CHECK в БД
  (`phone`, `name`, `email`) и заодно нормализует email в нижний регистр. Вход и смену
  пароля хук не трогает: формат пароля там сверять нечего (UC-G6 — общее сообщение),
  а «не короче 8» Better Auth проверяет сам.

Отвергнуто: своя реализация на argon2 + JWT (больше кода, цель — не auth);
Passport (не библиотека пользователей, только стратегии). Полный перебор — в D7.2.

## D7.1. Два драйвера Postgres — почему так

**Принято** (19.09.2026). Инвариант «SQL руками» (D5) относится к **коду проекта**, а не
к внутренностям зависимостей. Better Auth своих запросов нам не показывает и наших не
пишет, поэтому Kysely внутри него инвариант не нарушает.

postgres.js не подходит Better Auth технически: библиотека принимает либо инстанс
драйвера (`pg`, `mysql2`, `better-sqlite3`), либо диалект Kysely, либо адаптер ORM.
У postgres.js другой API (tagged templates вместо `query(text, values)`) и свой пул,
Kysely про него не знает. Значит выбор — между вторым пулом на `pg` и мостом к postgres.js.

Почему не свести всё к одному драйверу:

- **Всё на `pg`** — тогда весь прикладной SQL (а его на порядок больше, чем кода auth)
  пишется через `$1, $2` и отдельный массив значений, ради того чтобы модуль `auth`
  не заводил свой пул. postgres.js выбран в D5 именно за то, что запрос читается так же,
  как пишется, и за `sql.begin` вместо ручных `BEGIN`/`COMMIT`/`RELEASE`.
- **Всё на postgres.js через `kysely-postgres-js`** — community-диалект, передаётся
  как `dialect`. Один пул, но третья зависимость в самом чувствительном месте, не
  покрытая тестами ни Better Auth, ни Kysely. Отстанет от версий — чинить на защите.
- **Свой адаптер** через `createAdapter` — 200+ строк в той самой области, ради отказа
  от которой библиотеку и берут.

Цена двух пулов и что с ней делать:

1. **Два набора соединений.** `max` задаём явно обоим (`pg` — 5, postgres.js — 10),
   чтобы число было решением, а не значением по умолчанию.
2. **Две точки конфигурации и закрытия.** `DATABASE_URL` читается дважды; при shutdown
   закрываются оба — `sql.end()` в `DatabaseModule`, `pool.end()` в `AuthModule`.
3. **Нет общей транзакции между auth и нашим кодом** — разные соединения, разные `BEGIN`.
   У нас это не мешает: `phone` лежит `additionalFields` прямо в `users`, отдельной
   таблицы профиля нет, и регистрация — одна запись целиком внутри Better Auth.
   Заводить `profiles` теперь нельзя без пересмотра этого пункта.

## D7.2. Альтернативы Better Auth — перебор

**Принято** (19.09.2026). Требования: готовые регистрация/вход/роли (своё не пишем),
ORM в нашем коде нет, и — решающее — **пользователи лежат в нашей БД**, иначе
`test_drives.user_id → users.id` перестаёт быть внешним ключом.

| Вариант | Почему нет |
|---|---|
| **Auth.js / `@auth/core`** | построен вокруг OAuth; Credentials-провайдер регистрацию не делает вовсе — создание пользователя и хеширование пароля пишем сами, ролей нет |
| **Lucia** | депрекейтнута в марте 2025, пакета в npm нет: теперь это учебник «как написать сессии самому». Выбрать её = писать самому |
| **Passport** | не библиотека пользователей: регистрация, argon2, хранение сессий, роли — всё наше |
| **SuperTokens self-hosted** | закрывает всё (есть рецепт User Roles), но это отдельный контейнер со своей БД и своими миграциями |
| **Keycloak, Zitadel, Ory Kratos** | полноценный IdP: OIDC-редиректы, realms, админка. Для каталога из десяти автомобилей — несоразмерно |
| **Clerk, Auth0, WorkOS, Supabase Auth** | зависимость от интернета в момент защиты и регистрация в стороннем сервисе |

Общая беда всех вариантов с отдельным хранилищем (SuperTokens, IdP, облако): в нашей
базе пользователей нет, `test_drives.user_id` становится `text` с чужим идентификатором —
без FK, без `on delete`, без join к `users` для списка менеджера. Имя и телефон клиента
пришлось бы либо дублировать к себе, либо запрашивать по API на каждый рендер.

Better Auth — единственный, кто закрывает все три требования сразу. Запасной вариант,
если он не пройдёт spike S2, — **SuperTokens self-hosted**; переход означает пересмотр
связи с `users`, поэтому решается до первой миграции, а не после.

## D8. Общие типы — `packages/contracts` на zod

**Проверить** (spike S1).

- Контракт описывает **JSON на проводе**, а не сущности бэка: даты и деньги — строки,
  `numeric` из postgres.js и так приходит строкой.
- В пакете: zod-схемы запросов/ответов, выведенные типы (`z.infer`), общий формат ошибки,
  константы enum-ов (кузов, привод, статусы).
- **Бэкенд:** входящие body/query/params валидируются этими схемами через свой
  `ZodValidationPipe` (≈20 строк). Ответ типизируется выведенным типом.
- **Фронт:** типы для API-клиента и хуков TanStack Query; схемы форм (регистрация,
  тест-драйв) — те же, валидация на клиенте без дублирования.
- Ответы на фронте в рантайме **не** парсим — доверяем типам, бэк один и наш.
- Пакет собирается `tsc` в `dist` (ESM + `.d.ts`), в dev — `tsc --watch`. Nest импортирует
  собранный код, Vite — тоже. На spike проверить, что Nest (CJS) нормально импортирует
  ESM-пакет (Node 24 поддерживает `require(esm)`); если нет — собирать пакет в CJS.

Отвергнуто: общие DTO-классы Nest (декораторы и `reflect-metadata` в бандле фронта,
типы врут про даты и numeric); openapi-typescript (нужен, когда бэк не на TS);
ts-rest/oRPC (приятно, но ещё один слой — можно добавить позже поверх тех же схем).

## D9. Swagger не добавляем

**Принято.** Схемы в zod, а `@nestjs/swagger` живёт на декораторах классов — пришлось бы
описывать всё дважды.

Чем тестировать вместо него:
- **`.http`-файлы** в `apps/api/http/` — запросы в git, запускаются из VS Code
  (расширение REST Client) и JetBrains (встроено); cookie сессии сохраняются между
  запросами, так что сценарий «вход → запрос» работает.
- **e2e-тесты API** (Vitest + supertest) на отдельной тестовой БД в docker — ключевые
  сценарии: регистрация/вход, фильтры каталога, занятость слота тест-драйва, смена статуса записи.
- Если документация всё же понадобится — генерировать OpenAPI из zod-схем
  (zod 4 умеет JSON Schema), а не из декораторов.

## D10. Стили — CSS Modules + собственная дизайн-система на токенах

**Принято.** Аналог Tailwind + shadcn, но на чистом CSS.

- `styles/tokens.css` — два уровня переменных:
  - **примитивы:** шкалы цветов (`--gray-1…12`, `--accent-1…12`), `--space-*`,
    `--radius-*`, `--font-size-*`, `--shadow-*`, `--duration-*`, `--ease-*`;
  - **семантика:** `--color-bg`, `--color-surface`, `--color-fg`, `--color-fg-muted`,
    `--color-border`, `--color-primary`, `--color-primary-fg`, `--color-danger`, `--focus-ring`…
  - компоненты используют **только семантические** токены; тема = переопределение
    семантики под `[data-theme]`.
- `components/ui/*` — свои примитивы (Button, Input, Field, Card, Badge, Dialog, Select,
  Tabs, Skeleton, Toast). Варианты — через `data-variant` / `data-size` в CSS-модуле,
  классы склеиваются `clsx`.
- Поведение сложных компонентов (фокус, клавиатура, ARIA для Dialog/Select/Tabs/Toast) —
  **Radix Primitives** без стилей, как у shadcn. Простые компоненты — свои.
- Брейкпоинты — три фиксированных значения, записаны в tokens.css комментарием
  (кастомные media-переменные в CSS пока не поддерживаются); для карточек — container queries.

Отвергнуто: Tailwind/shadcn (хочется свой CSS), CSS-in-JS (рантайм, лишнее).

## D11. 3D — React Three Fiber + drei

**Проверить** (spike S3).

- `@react-three/fiber` — React-рендерер для three.js, `@react-three/drei` — готовые
  `OrbitControls`, `Environment`, `ContactShadows`, `useGLTF`, `Stage`.
- Модели: glTF/GLB, сжатие `gltf-transform` (Draco/Meshopt, текстуры в WebP/KTX2).
  Бюджет: ≤ 5–8 МБ на модель. Где хранятся — D15.
- Смена цвета кузова (только визуально) — меняем `color` материала краски; имя материала
  хранится у модели в БД.
- Страница просмотра грузится лениво (`React.lazy`), пока грузится — фото и лоадер;
  без WebGL или при ошибке — галерея вместо 3D.
- Источники: Sketchfab (проверять лицензию, CC-BY требует атрибуции), окружение HDRI —
  Poly Haven (CC0). Лицензии и авторов записываем в `docs/assets-licenses.md`.

Запасной вариант, если R3F не взлетит: `<model-viewer>` от Google — веб-компонент,
вращение и смена материала из коробки, но почти без контроля над сценой.

## D12. Деньги считает бэкенд

У автомобиля одна цена, конфигуратора цены нет (D18), поэтому считать на фронте нечего

## D14. Dev-окружение

**Принято.**
- Vite dev-сервер проксирует `/api` на Nest → фронт и API на одном origin: нет CORS,
  cookie Better Auth работают без настройки SameSite.
- Node 24, TypeScript strict везде, ESLint (flat config) + Prettier.
- Тесты: Vitest на обеих сторонах. `unplugin-swc` **не понадобился**: генератор Nest 12

## D15. Хранение 3D-моделей и фото

**Принято: статика.** Файлы кладём мы (seed), админ ничего не загружает — первый вариант ниже.

«Подгружать по необходимости» — это про клиент, а не про хранилище: модель скачивается
только при открытии вкладки 3D, где бы файл ни лежал. Хранилище выбирается по тому,
**кто пишет файлы**:

- **Файлы кладём мы (seed)** → статика, раздаётся nginx с долгим кешем
  (`Cache-Control: immutable`, хеш в имени). Бесплатный CDN — домен через прокси
  Cloudflare. В БД — относительный путь.
- **Файлы загружает админ** → S3-совместимое хранилище: MinIO в docker локально и на
  сервере (или Cloudflare R2 — бесплатный исходящий трафик). Загрузка по presigned URL
  прямо в хранилище, в БД — ключ объекта.

В обоих случаях: декодер Draco хостим сами (drei по умолчанию тянет его с внешнего CDN),
модели сжаты заранее, для каждой — превью-картинка.

Про Vercel: фронт как статика там хостится хорошо, но API на отдельном сервере — это
другой origin, и cookie сессии станут сторонними. Лечится rewrite `/api/*` на сервер
в настройках Vercel. Выигрыш по сравнению с «nginx + Cloudflare» небольшой, а точек
отказа две. Условия бесплатного тарифа Vercel проверить перед выбором.

## D15.1. Статику раздаёт Nest из `apps/api/public`

**Принято.** Фото автомобилей и `.glb` лежат в репозитории
(`apps/api/public/assets/cars/`, `apps/api/public/assets/models/`), пути к ним — в seed
(`/assets/cars/{slug}-1.webp`, `/assets/models/x5.glb`). Раздаёт их сам Nest:
`app.useStaticAssets(<apps/api>/public)` в `main.ts` — встроенная возможность
platform-express, новых зависимостей не требует.

Одинаково в dev и в проде: `/assets/*` отдаёт тот же процесс, что и `/api/*`,
отдельного шага сборки и копирования файлов нет. В dev фронт ходит туда через прокси
Vite — так же, как в `/api` (D14). Путь считается от `dist/main.js` (`dist/` → `apps/api/`),
поэтому `nest build` ничего в `dist` не копирует, а `public` остаётся рабочей копией.

Почему не nginx, как было записано в D15: nginx в проекте пока нет вообще, и заводить
его ради десятка файлов — конфиг, который придётся держать в двух видах (dev и прод).
Когда фронт поедет за nginx, раздачу `/assets` можно будет перенести туда одной строкой
конфига, ничего не меняя в коде и в БД — в БД лежит относительный путь. Долгий кеш
и хеш в имени (D15) тоже отложены: файлы не меняются, а версионировать нечего.

## D16. Роли: user, manager, admin

**Проверить** (spike S2).

- Admin-плагин Better Auth: поле `role`, `banned`/`banReason`/`banExpires` у пользователя,
  `impersonatedBy` у сессии; API `createUser`, `listUsers` (поиск, сортировка, пагинация),
  `setRole`, `setUserPassword`, `banUser`/`unbanUser`, `revokeUserSessions`.
- Роль `manager` — через `createAccessControl` плагина; `admin` включает права менеджера.
- На бэке `@Roles([...])` из `nestjs-better-auth` поверх глобального guard.
- Админ создаётся seed-скриптом; через UI роль `admin` не назначается.
- Удаление пользователей (`removeUser`) не используем — только блокировка.

## D17. Деплой

**Принято.** Один VM: docker compose (api, postgres, nginx со статикой фронта), HTTPS
обязателен (secure-cookie сессии). Разворачиваем **не в самом конце, а после этапа 6**
(авторизация) — чтобы проблемы с cookie, прокси и HTTPS всплыли заранее; дальше
обновляем по мере этапов.

## D18. Объём урезан: одна цена у автомобиля, минимум сущностей

**Принято** (19.09.2026). Первая версия схемы — 21 таблица с комплектациями, палитрой
с доплатами, избранным, сохранёнными конфигурациями, настройками салона и правилами
тест-драйва в триггерах. Для учебного проекта это работа, которая не окупается: половина
таблиц не была нужна ни одному сценарию, а правила в plpgsql дублировали бы правила в API.

Что решили:

- **Один автомобиль — одна цена.** Таблица `modifications` убрана, характеристики
  и цена живут в `cars`. Нет «цены от», нет выбора комплектации, нет расчёта конфигурации.
- **Избранное и сохранённые конфигурации убраны** вместе с таблицами.
- **Цвет — только внешний вид 3D-модели.** `car_colors` — связь многие-ко-многим
  без доплаты.
- **Правила тест-драйва — в API** (константы и код сервиса). В БД остались CHECK-и
  и частичный уникальный индекс занятости слота: его нельзя заменить кодом, он же
  решает гонку.
- **Настроек салона нет** — часы работы, горизонт, лимит и часовой пояс `Europe/Moscow`
  заданы константами; менять их через интерфейс некому.
- **У менеджера список записей на день**, а не сетка-календарь на неделю.
- **Админ только заводит менеджеров и смотрит пользователей**; блокировки и смены ролей
  в интерфейсе нет (колонки `banned`/`ban_*` остаются — их требует admin-плагин Better Auth).

Итог: 12 таблиц, связи и нормальные формы сохранены (справочники серий, кузовов и типов
двигателя, многие-ко-многим для палитры, две связи `users → test_drives`).
Подробности — [db/README.md](db/README.md), объём сервиса — [use-cases.md](use-cases.md).

## D19. Ключи — суррогатные, значение фильтра в URL — id

**Принято** (19.09.2026). Первая версия схемы использовала натуральные ключи:
`body_types.code = 'suv'`, `fuel_types.code = 'petrol'`. Это экономило join в каталоге
и делало и URL, и выборки читаемыми.

Решили иначе: **везде суррогатный `id`** (`bigint generated by default as identity`,
у таблиц Better Auth — `uuid`, его тип диктует библиотека). Натуральный ключ требует
доказательства, что значение уникально и никогда не изменится; суррогатный не требует
обоснования вообще. Для учебного проекта это снимает лишний спор на защите, а цена —
один join по справочнику из девяти строк — неизмерима.

Следствия:

- значение фильтра в URL — `id` (`/catalog?body=6`); фронт получает справочники
  из `/api/catalog/filters` вместе с их `id`;
- **порядок строк в справочных данных менять нельзя**, только дописывать в конец:
  id попадают в ссылки, а неверный id, в отличие от неверного кода, покажет не пусто,
  а другой кузов;
- текстовый `slug` остался у `cars` — это адрес страницы, а не значение фильтра;
- имена: ключ всегда `id`, внешний ключ — `<таблица>_id`. Пара `cars.id_car` + `car_id`
  отвергнута: в каждом join пришлось бы помнить, какое из двух имён где.

`car_colors` — исключение: там PK составной, `(car_id, color_id)`. Суррогатный ключ
у таблицы-связи без собственных атрибутов ничего не даёт, а уникальность пары всё равно
пришлось бы объявлять отдельно.

## D20. ESM везде, `contracts` собирается обычным `tsc`

**Принято** (19.09.2026, после `nest new`). Генератор Nest 12 предлагает выбор системы
модулей и по умолчанию ставит **ESM + Vitest**. Выбрали ESM.

Что это меняет по сравнению с первоначальным планом:

- **Общий формат модулей.** Nest раньше был CommonJS, Vite — ESM, и `packages/contracts`
  пришлось бы собирать в двух форматах с ветвлением в `exports`. Теперь обе стороны ESM,
  формат один.
- **tsup убран.** Один формат и декларации умеет обычный `tsc`. Вместе с tsup ушла
  заглушка `"ignoreDeprecations": "6.0"`, которая была нужна только из-за него.
- **`unplugin-swc` не нужен** — см. D14.
- **Правило импортов:** в `apps/api` и `packages/contracts` свои файлы импортируются
  с расширением `.js` (`./app.module.js`), хотя на диске лежит `.ts`. Этого требует
  `moduleResolution: "nodenext"`. На пакеты (`@nestjs/common`) правило не распространяется.
- **Линтер — ESLint.** Генератор Nest 12 кладёт `oxlint`; убрали, чтобы в репозитории
  был один линтер и один конфиг.

Отвергнуто: оставлять Nest на CommonJS (тогда двойная сборка контрактов остаётся
без причины); держать два линтера.
